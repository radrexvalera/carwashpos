# Changelog

Major implementation changes, newest first. This tracks the new 8-phase roadmap (OtoKwikk Car Wash Management System); see the git history before 2026-09-21 for the earlier, since-superseded simple-POS build (Phases 0–2 of the original scope).

## Phase 6b — Advanced: Fleet Accounts (2026-09-22)

Second Phase 6 slice: deferred/on-account billing for corporate fleet clients.

- **Fleet accounts**: `fleet_accounts` is a 1:1 add-on to a `company`-type `customer`, not a separate fleet↔vehicle join table — `vehicles.customer_id` already supports many vehicles per customer for free, so every vehicle under the account's customer *is* a fleet vehicle with zero new schema.
- **On-account sales**: `create_sale()` gained `billing_type = 'on_account'`, which relaxes the usual exact-payment-match requirement (a sale can be created with zero or partial payment; only overpayment is rejected), enforces the account's `credit_limit` against a running `fleet_account_balances` view (derived-sum, same discipline as `loyalty_balances`/`inventory_stock_levels` — no stored counter), and sets `payment_status` (`paid`/`partial`/`unpaid`).
- **Settlement**: `record_fleet_settlement()` pays down one specific invoice later — partial settlements allowed, capped to what's still owed on that sale so it can never overpay or go negative. Gated on a new `can_manage_fleet_accounts` permission (an office/accounting task, not tied to having an open shift the way `create_sale()` is). Backfilled onto the existing tenant's admin+manager roles directly, since the tenant-creation trigger's wildcard admin grant only covers tenants created from here on — and added to `seed_new_tenant_defaults()` so that stays correct going forward.
- **Bug caught during verification**: loyalty was earning immediately on an unpaid on-account sale, before any money had actually been collected. Fixed so earn only fires once a sale reaches `payment_status = 'paid'` — either at creation (an on-account sale that happens to be paid in full up front) or later when a settlement completes it — confirmed to fire exactly once either way.
- Frontend: Fleet Accounts admin page (search an existing customer or create a new company inline, credit limit/payment terms, outstanding invoices with a record-payment dialog), Collect Payment gained a "bill to fleet account" toggle showing available credit.
- Verified end-to-end via SQL under real RLS: credit-limit rejection and success after raising it, partial settlement reduces the balance correctly, over-settlement and settling an already-paid invoice are rejected, an inactive/nonexistent fleet account is rejected.
- Not yet built (remaining Phase 6 slices): memberships, appointments, vehicle inspections.

## Phase 6a — Advanced: Promotions & Loyalty Points (2026-09-22)

Phase 6 ("advanced": promotions, loyalty, memberships, fleet accounts, appointments, vehicle inspections) is being delivered incrementally. This slice covers promotions + loyalty, since both hook into the same place — `create_sale()`'s discount computation.

- **Promotions**: `promotions`/`promotion_services` — staff-applied at checkout (cashier picks from a list, no customer-facing codes), percentage or fixed-peso off, optionally restricted to specific services, an optional minimum spend, and an optional date range. Computed and validated entirely server-side inside `create_sale()`, layered on top of the existing manual per-line discount without changing that path at all.
- **Loyalty**: `loyalty_transactions` — an append-only points ledger, same discipline as `commission_ledger`/`inventory_transactions` (balance is always a derived sum via the `loyalty_balances` view, never a stored counter that could drift). Points earn on a completed sale (based on money actually collected, post every discount) and can be redeemed for a peso-value discount at checkout; redemption is capped to what the sale can actually absorb rather than trusting the requested amount. `loyalty_earn_rate`/`loyalty_redemption_value` are tenant-tunable via Settings. `adjust_loyalty_points()` is the manual-correction escape hatch (gated, requires a reason), mirroring `adjust_inventory_stock()`.
- `sales` gained `customer_id` (resolved server-side from the job's vehicle), `promotion_id`, `promotion_discount_amount`, `loyalty_points_redeemed`, `loyalty_discount_amount` — all covered by the existing tamper-guard trigger.
- Frontend: Promotions admin page (with a per-service restriction picker), Loyalty page (customer search, balance, history, manual adjustment dialog), Collect Payment gained a promotion selector and points-redemption input with a client-side preview (the server remains authoritative), Sales Report gained a promotions & loyalty stat.
- Verified end-to-end via SQL under real RLS: a percentage promotion computes correctly and rejects a sale below its minimum spend; a customer earns points on a completed sale; redemption reduces both the sale total and the loyalty balance correctly and is capped (not the customer's full requested amount) when it would exceed the remaining total; the existing `client_generated_id` idempotency replay still works with the new fields attached; the manual adjustment RPC enforces its permission and non-empty-reason checks.
- Not yet built (later Phase 6 slices): memberships, fleet accounts (confirmed direction: deferred/on-account billing), appointments, vehicle inspections.

## Phase 5 — Management: Expenses & Reports (2026-09-22)

- **Expenses**: `expenses`/`expense_categories`, following the same discipline as every other ledger in the app — no direct insert/update policy, `record_expense()`/`void_expense()` (gated by `can_manage_expenses`) are the only write paths, and a trigger (`prevent_expense_tampering`) blocks editing a recorded expense's financial/identity fields after the fact. A correction is a void with a required reason, never a row edit. Deliberately standalone from `cash_movements`/shift reconciliation for v1, since most operating expenses (rent, utilities) aren't paid out of the till.
- **Sales Report**: revenue by payment method, service vs. product revenue split, top services, discounts given, voided-sale count, and expenses by category, over a chosen date range — computed client-side from `sales`/`payments`/`sale_items`/`expenses`, no new base tables (reports are queries over existing data, per the original Phase 5 design).
- **Owner Dashboard**: the placeholder Dashboard page is now a real summary — today's sales/expenses/net, pending (unpaid) commission, active jobs by status, jobs completed today, and low-stock item count with a link to Inventory.
- Verified: `can_manage_expenses` confirmed granted to admin/manager on the live tenant, default expense categories (Rent/Utilities/Salaries & Wages/Supplies/Equipment & Maintenance/Marketing/Miscellaneous) seeded, `tsc -b` and `npm run build` clean.

## Phase 4 — Inventory (2026-09-22)

- **Items & ledger**: `inventory_items` (retail/consumable/reusable_equipment/asset) has no stock or cost columns of its own — `inventory_transactions` is the single append-only source of truth (opening_balance/purchase/stock_in/service_consumption/retail_sale/adjustment_positive/adjustment_negative/damaged/expired/lost/returned/transfer/manual_correction). `record_inventory_transaction()` is the sole write path: it computes `previous_qty`/`new_qty` server-side under a `pg_advisory_xact_lock` per item, so concurrent writers can't race. `inventory_stock_levels` is a `security_invoker` view aggregating the ledger into on-hand/avg-cost/value per item.
- **Manual adjustments**: `adjust_inventory_stock()` is the client-facing wrapper — requires `can_manage_inventory` and a non-empty reason, never a bare quantity overwrite.
- **Categories & units**: `inventory_categories` (sortable) and `inventory_units` (with a base-unit conversion factor, e.g. "liters per gallon") for reporting/recipe consistency.
- **Service recipes**: `service_recipe_items` — expected consumable usage per service, optionally per vehicle size (a size-specific row overrides the "any size" default for the same item). `complete_job()` (Phase 3) was extended to also walk each completing job_service's recipe and post a `service_consumption` transaction in the same DB transaction as the commission entries — same idempotency guarantee (a repeated completion call is a no-op).
- **Purchasing**: `suppliers`, `purchase_orders`/`purchase_order_items`. `create_purchase_order()` posts one `stock_in` transaction per line atomically with the order, so recording a purchase immediately reflects in stock on hand.
- **Retail integrated into POS**: dropped the old `products`/`consumables`/`service_bom` tables (confirmed zero real rows, CASCADE-dropped along with the legacy `ticket_line_items` FK and `ticket_board_entries` view that depended on them). `sale_items.product_id` renamed to `item_id`, now pointing at `inventory_items`. `create_sale()` reworked to price retail lines from `inventory_items.retail_price` and deduct stock via a `retail_sale` transaction instead of a direct `UPDATE`. The Collect Payment screen (`JobPaymentPage`) now has a product picker so a cashier can ring up a retail item (e.g. air freshener) on the same sale as the job's services.
- Frontend: Inventory Items (stock levels + adjust dialog with transaction history), Purchases, Suppliers, Service Recipes, Inventory Categories, Inventory Units — all admin/manager-gated.
- Verified end-to-end via SQL under real RLS: purchase → stock-in reflected in stock levels; job completion → auto-consumption deducts recipe items exactly once even on repeated completion calls; manual adjustment rejected without a reason; retail sale deducts stock.

## Phase 3 — Commission (2026-09-21/22)

- **Commission rules**: one rule per service, or a tenant-wide default used as fallback. Supports fixed-pool, percentage-of-price, fixed-per-attendant, and points methods directly; custom/role-based splits work via a per-attendant split-percentage override on the existing crew assignment (no separate role-rate table needed).
- **Commission ledger**: a proper append-only ledger — a reversal will be a new row referencing what it reverses, never an edit to the original.
- **`complete_job()`**: the "Picked up" action now completes every open job-service line and computes commission for each atomically, in one transaction — idempotent (a repeated call is a no-op), and independent of whether the job has been paid for yet.
- **My Commission**: an attendant's (or anyone's) own today's-earnings dashboard + recent history.
- **Commission Report**: manager view, totals by employee then by service, for a date range.
- Verified via SQL under real RLS enforcement: a 2-attendant fixed-pool job splits evenly, a repeat completion doesn't double-pay, and a 70/30 custom split computes correctly.
- Known gap: no UI yet to set a custom split percentage at crew-assignment time — works end-to-end at the schema/RPC level, needs a Register control.
- **Payroll periods**: `generate_payroll_period()` rolls unclaimed commission into one entry per employee for a date range (daily/weekly/semi-monthly/custom); manual fields (base pay/tips/bonus/cash advance/deductions) are editable while a period is a draft, `net_pay` is a generated column; `lock_payroll_period()` freezes entries (enforced by RLS, not just UI); `mark_payroll_period_paid()` propagates paid status back onto the commission ledger. Post-lock corrections are new `payroll_adjustments` rows, never edits. This closes out Phase 3.

## Phase 2 — Core Car Wash POS (2026-09-21)

- **Customers/vehicles**: registered customers are optional (a walk-in vehicle has no `customer_id` at all); vehicle make/model are free text, never FKs — the make/model lookup is only a convenience default. No stored `total_visits`/`total_spend`/`last_visit`/`loyalty_points` on customers — derived from jobs/sales at read time instead of mutable counters that could drift.
- **Jobs**: `jobs` / `job_services` / `job_service_attendants` / `job_status_history`. A job is the shop-floor unit of work, created independent of payment. Attendants are assigned per SERVICE LINE, not per job, so different crew can work different services on the same vehicle — this is what Phase 3's commission ledger will key off of. `create_job()` prices every service server-side and assigns a `JOB-YYYYMMDD-NNNN` number, atomically, with crew assignments.
- **Sales/payments**: `sales` / `sale_items` / `payments`, plus `wash_bays` (renamed from `bays`), `cashier_shifts` / `cash_movements`. A sale is deliberately decoupled from job status — created whenever payment is collected, not gated by job completion — but requires an open shift. `create_sale()` bills job-service lines (with an optional checkout-time discount) or retail products, prevents double-billing the same job-service, and validates split payments. `close_shift()` computes expected cash from the actual sales/cash-movement ledger, never a client-supplied figure.
- Frontend: the old ticket-based POS and bay board are **retired** (deleted, superseded) in favor of Register (job builder) → Job Queue (Kanban board, live via Realtime) → Collect Payment (reached from an unpaid job card) → My Shift. Payment collection is online-only by design; job creation and shop-floor status updates remain offline-capable via the same outbox pattern as before.
- All backend logic verified end-to-end via SQL under real RLS enforcement (not the `postgres`-role bypass `db query` normally runs as): shift → job → crew assignment → split-payment sale → double-bill rejection → cash reconciliation.

## Phase 1 — Foundation (2026-09-21)

- **RBAC**: capability-based `permissions` / `roles` / `role_permissions` / `employee_roles`, plus a `has_permission()` RLS helper. Additive alongside the existing `user_profiles.role` mechanism, which still drives the old Phase 0–2 tables untouched.
- **Employees**: a registry separate from login-linked `user_profiles`, since many attendants never log in. Supports multiple roles per employee.
- **Vehicle taxonomy rework**: collapsed the old two-axis classification (Motorcycle-Small/Big + S/M/L/XL/XXL, and a separate Sedan/Crossover/SUV/Van used only by Tint) onto a single 6-tier ladder — Motorcycle/Small/Medium/Large/XL/XXL — used for all pricing. `vehicle_makes`/`vehicle_models` added as a convenience lookup (never drives pricing). Existing OtoKwikk pricing data remapped onto the new ladder.
- **Service catalog rework**: `service_categories` replaces the old free-text category column; `services` gained `pricing_type` (matrix/flat/starting_at/quoted) and `flat_price` for non-matrix services.
- **Settings**: one configurable business-info row per tenant (name, address, contact, receipt header/footer, numbering prefix).
- Frontend: Employees and Settings admin pages (first use of react-hook-form + zod, now the established pattern for future forms); catalog admin pages reworked for the renamed tables.

## Earlier build (superseded)

A simpler payment-first ticket POS + bay board was built first (see git history before this changelog existed) and is being replaced by this roadmap's job/sale model, starting with Phase 2. The original service catalog and real OtoKwikk pricing data were carried forward into this rebuild.
